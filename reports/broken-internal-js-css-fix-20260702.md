# Broken Internal JS/CSS Fix - 2026-07-02

## Root Cause Found

The CSV report showed 14 internal JavaScript 404s and no CSS failures. The missing files were stale Next.js page chunks:

- `/_next/static/chunks/pages/product-c6c23d4628024587.js`
- `/_next/static/chunks/pages/product-category/[slug]-e0fa10a9791146b2.js`

The affected routes are server-rendered pages. Source search found no hard-coded stale chunk references in active source or current output; the old names appeared in the CSV and old local verification build folders. The likely production failure mode was stale rendered HTML/build-manifest data outliving the static chunk set after a build/deploy. One affected route, `product-category/[slug]`, explicitly set public edge caching for rendered HTML, which can preserve old hashed asset references across deployments.

## Files Changed

- `src/lib/cacheHeaders.ts`
- `src/pages/product.tsx`
- `src/pages/product-category/[slug].tsx`
- `public/sitemap.xml` regenerated by the configured `postbuild` step
- `reports/broken-internal-js-css-fix-20260702.md`

Generated verification output:

- `.next-js-css-fix-20260702/`

Note: another local Next process was touching the default `.next/` directory during verification, so the final production crawl used the existing `NEXT_DIST_DIR` support to validate an isolated clean build.

## Fix Applied

- Added `setNoStoreCache()` for dynamic HTML responses.
- Applied explicit `Cache-Control: no-store, no-cache, must-revalidate, proxy-revalidate` to `/product`.
- Replaced public edge caching with explicit no-store caching on `/product-category/[slug]`.
- Kept hashed static asset caching unchanged for `/_next/static`.
